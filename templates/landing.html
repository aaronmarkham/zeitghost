I.

You've built this before.

folio i — the ache

There's no standard library for the layer beneath the agent. So you keep rebuilding it — and the part everyone skips is the part that would let you prove any of it.

— filed under /substrate

Every agentic app re-solves the same problems. When something goes wrong three steps back, can you prove what actually happened — or only reconstruct it from whatever the run happened to print? Where does what the agent learned live, and how do you keep it from drifting into contradiction? How do you hand a sub-task to another agent without handing over the keys to everything?

So you rebuild the glue for each app, slightly different every time. Or you eat the misalignments, the delegation failures, the memory drift. Or you rent a managed service that takes custody of your data and your latency budget.

Few teams do provable tracing or scoped entitlements without standing up heavy infrastructure, so the hardest question — what actually happened? — gets answered by logs the system wrote about itself. The layer beneath the agent has been left to improvisation: re-glued in every codebase, owned by none of them, and taken on faith.

II.

One substrate. Trust is a dial.

folio ii — the idea

The layer your stack is missing.

spiritwriter is content-addressed memory, hash-chained traces, scoped entitlements, computed identity, and deterministic entity resolution. Composable primitives with one property in common: each produces something that can be checked independently, without taking the system's word for it. Dial them from fully public and provable to fully private and zero-knowledge by changing one setting.

Bring your own everything-else. spiritwriter handles what those layers leave out.

  • memorycontent-addressed shards — same content, same id.
  • provenancehash-chained traces, signable and chain-verifiable.
  • delegationscoped entitlements, enforced before decrypt.
  • identitycanonical forms, computed rather than registered.
  • resolutiondeterministic entity IDs, no embeddings.

It's not an agent framework, and it's not a vector database. It's what those sit on.

IV.

Slip it under what you already run.

folio iv — adoption

Additive, not a migration.

Store what your agent learns, hydrate it back into a prompt later. Get provenance on day one; lean on delegation and zero-knowledge when you're ready.

  • local-firstshards are JSON on disk; the index is one JSON file. No daemon, nothing leaves your machine.
  • agent-readableevery capability ships a skill file — your agent learns the primitives by reading it.
  • cheap to leavefiles you own, Apache 2.0. Low exit cost, low risk to try.
  • no hostnothing to host means nothing to bill — no vendor in the middle of your data.
from spiritwriter.fabric.shard import (
    MemoryShard, ShardAtom, AtomKind, DecayClass,
)
from spiritwriter.fabric.store import ShardStore

store = ShardStore("~/.myapp/shards")

shard = MemoryShard(
    atoms=[
        ShardAtom(
            text="Project uses FastAPI",
            kind=AtomKind.FACT,
            entity="myproject",
            key="framework",
            value="FastAPI",
        ),
        ShardAtom(
            text="Always run migrations before deploy",
            kind=AtomKind.CONVENTION,
            entity="myproject",
            key="deploy_rule",
            value="migrations-first",
        ),
    ],
    scope="project:myproject",
    origin="dev-agent",
    decay_class=DecayClass.STABLE,
)

ref     = store.put(shard)        # idempotent — same content, same id
context = store.hydrate([ref])    # XML-tagged, prompt-ready
V.

We measured it. We tried to break it.

folio v — the numbers

Entity resolution is where memory systems quietly corrupt themselves — merging two different people, or splitting one across three records. So we held it to a falsification battery, not vibes.

100% auto-merge precision — zero incorrect merges across five benchmark corpora. And it surfaces 100% of same-entity matches: auto-merging the safe ones, flagging the rest for review, so nothing slips through silently.

No embeddings, no LLM in the merge path — deterministic hashing, normalization, and tiered escalation that fails loud instead of silently combining two different people. Backed by a falsification battery, a workshop curriculum, and runnable examples.

VI.

Some things don't need a score.

folio vi — the exact half

Resolution answers are these the same? with a confidence. Some records don't have a confidence to give. Where a structure carries a symmetry it is allowed to have — a ring of references read from a different starting point, co-equal members listed in another order — the two records aren't similar. They're the same thing written twice.

spiritwriter computes the one canonical form of that structure, and a digest of it. Two systems that have never communicated arrive at the same value because there is only one value to arrive at. No registry to consult, no identifier service, no coordination beyond the operations themselves.

Similarity can't stand in for it. Across 200 such pairs the rule settles every one with no wrong merges, while the best cutoff that makes no wrong merges catches none. Structural variation isn't a weak signal waiting to be tuned — the score points the wrong way.

VII.

What it ends.

folio vii — what you get
Memory that drifts into contradiction Content-addressed shards with lineage, supersession, and decay.
"Can I let a sub-agent see this?" Scoped entitlements — keys + scope + capabilities + budget, enforced before decrypt.
"What did the agent actually do?" Hash-chained, signable traces you can verify offline.
Duplicate / colliding entities Deterministic-then-fuzzy resolution, no embeddings.
Privacy vs. transparency The same dial — AES, sealed boxes, or fully public.
Sharing across machines Private IPFS swarm, no database.
